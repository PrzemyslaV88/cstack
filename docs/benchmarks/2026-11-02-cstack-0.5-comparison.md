# cStack 0.5: fresh single-agent and multi-agent bug-fix comparison

Run date: 2 November 2026 (Australia/Perth). Ten real Codex trials: the same five historical bugs in each cStack mode. No new pstack or plain-Codex trials were run.

The measured result is mixed: multi-agent used 6.7% fewer total tokens and 15.8% less task time; single-agent used 12.1% more total tokens and 5.3% more time. Both still passed all five bug tasks.

Each mode is compared with its own most recent five-case cStack results. The model, reasoning effort, CLI version, frozen task images, public reproductions, hidden tests and per-trial limits were preserved.

| Mode | Private-test passes, old → new | Tokens, old → new | Token change | Task time, old → new | Time change |

| Single agent | 5/5 → 5/5 | 773,930 → 867,374 | +12.1% | 329.0s → 346.4s | +5.3% |

## What the results establish

The independent private grader passed 10 of 10 candidate repairs. Native logs account for all 10 parent runs and 10 helper agents, using the same model and medium effort. There were no charged retries of trials, and token accounting was complete.

cStack still requires human review on 10 candidates because they changed protected tests or configuration. A private-test pass does not remove that review gate. No human approval was fabricated. 10 of 10 repairs used one controller attempt.

Task time covers the agent/controller execution stage, including controller checks and candidate delivery. It excludes worker provisioning and the separate private grading stage. The actual operator wait is longer.

## Scope and limitations

- One new trial per mode/bug; historical comparison with model/cache/service variation does not establish causal speedup.
- Tokens include cached input once and all helpers; not billed cost or full outer-chat cost.
- Task time excludes provisioning and private grading. Controller verification and private grader pass are separate; human review is not synthesized.
- Multi-agent benchmark adapter remains experimental; every helper uses the same model family, reducing review diversity.
- All ten repairs used one controller attempt, so retry and resumed-context optimizations were not exercised.
- This exercise tests fixing the same bugs. Setup, profile creation, delivery UX and other new plugin workflows are not end-to-end measurements here.

## Exact protocol differences

- Current 0.5 controller with schema-3 evidence-v1 context; no hand-picked source hints.
- Public criterion bytes and expected outcomes, worker/public/private images, model, effort, CLI, CPU allocation and per-trial limits preserved.
- Full issue remains in the bounded goal. Complete frozen public reproduction is appended to the initial worker prompt and remains in resumed native conversation.
- Transport returns native root thread identity, enabling resumed context omission. Admission charges parent/helper cumulative deltas.
- Single mode disables delegation. Multi mode uses one code writer and two actual native read-only helpers; all seats use the same model and effort.
- Setup/profile convenience and new pytest/Vitest adapters are not exercised: historical public probes and separate upstream private tests remain identical.

The schema-3 goal-size preflight initially rejected the longest issue when the full reproduction was embedded inside the goal. This was fixed before any model trial: the complete issue stays in the goal, and the unmodified public reproduction is attached to the first worker prompt. Failed preparation artifacts were retained; no paid/model trial was discarded.
